# Cross-type validation: Passport vNext в целевом сегменте KEY

**Версия:** 0.2  
**Дата:** 2026-11-06  
**Статус:** архитектурная проверка и зафиксированное ограничение первой версии; не production schema.

## 1. Продуктовая граница

KEY на текущем этапе работает только с новостройками бизнес- и премиум-сегмента в городских локациях.

В целевой рынок входят:
- клубные дома;
- городские жилые проекты бизнес- и премиум-класса;
- проекты с несколькими корпусами и/или очередями, если они соответствуют выбранному сегменту;
- проекты с выраженной архитектурной концепцией, качественной городской локацией, приватной средой и характерными продуктовыми особенностями.

Вне текущего scope:
- массовая типовая застройка и эконом/стандарт-сегмент;
- загородная недвижимость;
- коттеджные посёлки;
- самостоятельная продажа земельных участков.

Это осознанный выбор фокуса при ограниченных ресурсах, а не утверждение, что будущая система никогда не сможет поддержать другие сегменты. Расширение допускается только при подтверждённой бизнес-потребности и отдельном решении. Не проектировать такие домены заранее.

## 2. Три сценария проверки внутри выбранного рынка

Сценарии являются типовыми архитектурными профилями. Они не описывают конкретные объекты и не добавляют неподтверждённые сведения в паспорта.

### A. Клубный дом

Проверяем:
- один городской проект и одна основная территория;
- один корпус или здание;
- небольшое число квартир;
- особенности архитектуры и фасадов;
- лобби, приватные общественные пространства, двор;
- террасы, панорамное остекление, высота потолков и другие особенности квартир — только если подтверждены;
- подземный/наземный паркинг, келлеры, машиноместа и иные отдельные продуктовые единицы;
- внешнюю инфраструктуру и фактические маршруты.

Вывод: базовые Project, Organization, Building, Property Unit, Plan, Site Feature, POI, Route, Claim, Source, Evidence и Asset покрывают сценарий.

### B. Премиальный многокорпусный жилой комплекс

Проверяем:
- один проект с несколькими корпусами;
- очереди строительства, если они есть;
- корпуса с разными характеристиками и сроками;
- секции, этажи и продуктовые единицы;
- общую территорию и отдельные пространства каждого корпуса;
- общие и корпусные коммерческие условия;
- отдельный прогресс строительства по корпусам;
- разные наборы планировок и активов.

Вывод: модель должна связывать claims, documents, construction events, plans, units и assets с конкретным корпусом/очередью. Значение на уровне проекта нельзя автоматически распространять на каждый корпус.

### C. Городской проект бизнес-класса с разными форматами жилья

Проверяем:
- один городской проект;
- один или несколько корпусов;
- квартиры разных типов, в том числе нестандартные форматы;
- апартаменты, если юридический и продуктовый статус подтверждён;
- коммерческие помещения, машиноместа и кладовые, если они входят в продукт;
- террасы, пентхаусы, двухуровневые и другие особенности как типизированные характеристики, а не произвольные маркетинговые ярлыки;
- разные планировки и предложения по конкретным единицам.

Вывод: нужен общий Property Unit с контролируемым типом и необязательными/условными атрибутами. Не следует создавать отдельную сущность для каждого маркетингового формата квартиры.

## 4. Целевой контракт сущностей первой версии

### Project
Идентичность городского жилого проекта: ID, название, aliases, класс/сегмент как подтверждаемое утверждение, адрес, координаты, район, external IDs и связи с организациями.

Класс и сегмент нельзя назначать по субъективному впечатлению. Источник, метод определения и статус должны быть сохранены.

### Organization
Застройщик, юридическое лицо, архитектурное бюро, генподрядчик, управляющая организация и иные участники. Роль организации задаётся явно; бренд и юридическое лицо не смешиваются.

### Phase
Необязательная очередь/этап проекта. Используется только если проект реально разделён на очереди или этапы. Не вводить искусственную фазу для каждого объекта.

### Building
Корпус/здание с собственным ID, номером/названием, связью с проектом и фазой, характеристиками, секциями, этажностью, лифтами, инженерными системами и строительными статусами. Значения, влияющие на публичные заявления, связываются с Claims/Evidence.

### Section
Необязательная секция/подъезд внутри здания. Нужна для привязки планировок, этажей, лотов и документов, когда источники различают секции.

### Property Unit
Конкретная единица недвижимости или отдельный объект предложения. Контролируемый unitKind первой версии:
- apartment;
- apartment_with_terrace — только если такой формат реально выделен в источниках и каталоге;
- serviced_apartment — только при подтверждённом юридическом/продуктовом статусе;
- commercial_unit;
- parking_space;
- storage_unit;
- other.

Пентхаус, двухуровневая квартира и видовая квартира не обязательно отдельные unitKind: это могут быть типизированные features конкретной квартиры. Не создавать поля rooms для машиноместа и не требовать план квартиры для кладовой.

Property Unit может иметь buildingId, sectionId, floor, planId, area, rooms, featureIds, availabilityStatus и ссылки на актуальные commercial terms. Поля зависят от типа единицы. Цена и наличие имеют дату наблюдения и срок актуальности.

### Plan
Типизированные схемы первой версии:
- apartment_floor_plan;
- building_floor_plan;
- section_plan;
- floor_plan;
- site_masterplan;
- parking_plan;
- other.

У плана есть ID, kind, version, asset reference, subject reference, площадь/параметры при применимости, geometry/scale status и evidence. Планировка как тип решения не равна конкретной квартире и не доказывает её наличие.

### Site
Территория городского проекта: граница/геометрия или ссылка на неё, площадь при наличии доказательства, связь с проектом, корпусами и внутренними зонами. Site не доказывает право собственности или доступность всей изображённой территории.

### Site Features
Внутренние пространства и элементы среды проекта:
- lobby;
- courtyard;
- private_garden;
- terrace;
- playground;
- sports_area;
- lounge;
- coworking;
- concierge_area;
- parking;
- storage;
- other.

Это отдельные элементы проекта, а не внешние POI. Для каждого фиксируются тип, расположение/связь с корпусом, статус (запроектировано, заявлено, строится, реализовано, неизвестно), claims и evidence.

### POI и Routes
POI — внешний объект городской инфраструктуры. Внутренние зоны проекта относятся к Site Features. Маршрут — отдельная сущность с точками начала/конца, способом передвижения, расстоянием, временем, источником расчёта и временем наблюдения. Прямая дистанция не равна маршруту.

### Documents и Construction Events
Документы имеют subject scope: project, phase, building, section или property unit. Редакции и даты сохраняются, новая декларация не затирает историю. Construction Event описывает наблюдаемое/заявленное событие и привязан к точному объекту, к которому оно относится.

### Commercial Terms
Цена, скидка, рассрочка, ипотечная программа, бронирование и другие условия. Условия имеют область действия, период действия, ограничения, источник и evidence. Сценарии получения лида KEY не являются Commercial Terms и остаются в Conversion Catalog / Landing Brief.

### Assets
Фото, рендер, видео, план, документ, карта и графический материал. Обязательны тип представления, depicted entity, роль, версия, правообладатель, статус прав и разрешённые контексты использования. URL не означает наличие разрешения на публикацию.

### Claims, Sources, Evidence
Claims — атомарные проверяемые утверждения. Source — источник. Evidence — конкретное место/фрагмент, подтверждающий claim. Статус знания, модальность заявления, актуальность и разрешение на публикацию остаются независимыми полями.

## 5. Специфика бизнес- и премиум-сегмента: что собирать, но не предполагать

Паспорт должен позволять структурированно хранить следующие характеристики, если они существуют и подтверждены:
- архитектурная концепция, автор/бюро, концептуальные решения;
- фасадные материалы и конструктивные особенности;
- этажность, число квартир, плотность и число квартир на этаже;
- лобби, ресепшен, консьерж-сервис и общественные пространства;
- приватность, контроль доступа и режим территории — без абсолютных обещаний безопасности;
- двор, озеленение, приватные сады и благоустройство;
- террасы, панорамное остекление, высота потолков и нестандартные планировки;
- инженерные системы, вентиляция, кондиционирование и лифты;
- паркинг, машиноместа, кладовые и инфраструктура для автомобилей;
- отделка и комплектация;
- видовые характеристики — с привязкой к конкретной квартире/этажу и подтверждением;
- городская инфраструктура и маршруты.

Это перечень допустимых доменов сбора данных, а не чек-лист обязательных преимуществ каждого проекта. Отсутствующее поле не должно порождать выдуманное преимущество.

## 6. Что сознательно не входит в первую версию

Не проектировать сейчас:
- Land Parcels как домен продажи участков;
- коттеджи, таунхаусы как загородный формат, участки и подряд на строительство;
- сельские/загородные сети, дороги и инфраструктуру посёлка;
- универсальную модель всех видов недвижимости;
- отдельные схемы для массового жилья.

Не создавать абстрактные extension registries, plugin-системы типов или произвольные атрибуты «на будущее». Если появится реальная потребность в новом сегменте, сначала будет оформлен бизнес-кейс, затем отдельная версия модели и миграция.

## 7. Архитектурные инварианты

1. Паспорт описывает объект и доказательства, не маркетинговую стратегию кампании.
2. Сегмент KEY ограничивает текущую область применения, но не подменяет доказательства конкретного класса объекта.
3. Каждое динамическое значение (срок, цена, наличие, маршрут, статус строительства) имеет дату наблюдения и правила актуальности.
4. Проектное заявление не превращается в подтверждение физической реализации.
5. План не равен лоту; планировка не доказывает наличие.
6. Внутренние Site Features не смешиваются с внешними POI.
7. Общее значение проекта не распространяется автоматически на корпус, секцию или квартиру.
8. Asset без разрешения не попадает в публичную проекцию.
9. Неполнота одного домена не блокирует независимые модули.
10. Market Context и закрытые сведения не попадают в public runtime.
11. Новые типы добавляются по доказанной потребности, а не из желания заранее покрыть весь рынок.

## 8. Решение по следующему этапу

Проверка трёх сценариев внутри текущей ниши пройдена на уровне логической модели. Перед JSON Schema 2.0.0 остаются задачи:
1. сверить новые сущности с реальными consumers текущего runtime;
2. определить минимальный обязательный набор полей и conditional rules для Property Unit;
3. определить единый формат subject references для claims/documents/assets/events;
4. определить формат Site Features и связи с корпусами;
5. подготовить mapping текущих полей 1.0.0 и список потерь/неоднозначностей;
6. добавить schema fixtures и negative tests.

До выполнения этих задач текущая schema 1.0.0 остаётся production contract. Этот документ и Passport vNext proposal не включают автоматическую миграцию и не меняют runtime.
