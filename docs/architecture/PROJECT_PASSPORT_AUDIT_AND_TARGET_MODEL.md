# Аудит паспорта ЖК и целевая модель данных KEY

**Версия:** 0.1  
**Статус:** архитектурное предложение после аудита текущих контрактов  
**Назначение:** определить, какие знания должна собирать KEY для автономного создания обоснованных, индивидуальных и конверсионных лендингов.  
**Важно:** документ не вводит новую параллельную схему и не меняет текущий JSON-контракт. Он задаёт границы ответственности, целевые домены и безопасный план эволюции.

**Полевой аудит текущего паспорта:** [PROJECT_PASSPORT_FIELD_AUDIT_KD_905_2026-11-06.md](../audits/PROJECT_PASSPORT_FIELD_AUDIT_KD_905_2026-11-06.md). Он классифицирует поля схемы 1.0.0, fixture 905 и фактические зависимости runtime; до отдельного migration proposal текущий schema contract не меняется.

## 1. Архитектурный вывод

KEY уже имеет четыре самостоятельных информационных слоя:

1. **Project Passport** — сведения о конкретном объекте и доказательства этих сведений.
2. **Customer Experience** — исследования покупателей, сегменты, JTBD, барьеры, CJM, ценностные предложения и измерение.
3. **Landing Brief** — стратегия конкретной кампании: фокус, позиционирование, hooks, офферы, воронки, CTA, квалификация и эксперименты.
4. **Landing Runtime / Manifest** — утверждённая конфигурация страницы: контент, модули, порядок, активы и интеграционные параметры.

Эти слои нельзя объединять в один огромный паспорт. Автономность достигается не количеством полей в одном JSON, а качеством связей и передач между слоями.

Целевая цепочка:

`source → evidence → project knowledge → market/customer research → campaign strategy → landing specification → runtime → lead outcome → learning`

У каждого решения должен быть обратный путь к основаниям: источник, исследовательское наблюдение или явно помеченная гипотеза.

## 2. Что обнаружено в текущей реализации

### 2.1 Уже есть — не дублировать

| Область | Текущий контракт | Оценка |
|---|---|---|
| Идентификация проекта, застройщик, адрес, район, базовые параметры | `project-passport.schema.json / project` | Есть основа, но пока ограниченная глубина модели |
| Атомарные публичные утверждения и разрешение на публикацию | `facts`, `$defs/fact` | Полезная база; нужно постепенно усилить типизацию и связи |
| Источники и подтверждения отдельных значений | `source`, `evidencedValue` | Есть, но одна и та же информация описывается разными способами |
| Преимущества, инфраструктура, предложения | `advantages`, `infrastructure`, `offers` | Есть, но некоторые сущности уже содержат маркетинговую интерпретацию |
| Медиа, документы, планы и права | `assets` | Есть базовый реестр активов; не хватает более богатых метаданных и связей |
| Планировки | `apartmentPlans` | Есть базовая модель планировки, но не полноценная модель корпуса/секции/этажа/лота |
| Рыночные наблюдения | `marketContext` | Добавлен; верно изолирован от публичного runtime |
| Сегменты, JTBD, мотивы, страхи, барьеры, доказательства | `customer-experience.schema.json` | Уже выделено отдельно — расширять этот контракт, не паспорт |
| Journey/CJM, touchpoints, value proposition, метрики | Customer Experience | Есть основа для поведения и клиентского пути |
| Позиционирование, hooks, offers, funnels, CTA, qualification, experiments | `landing-brief.schema.json` | Отдельный кампанийный слой — правильная граница |
| Состав и порядок секций | module catalog + runtime manifest | Не переносить решения композиции в исходный паспорт |

### 2.2 Архитектурные смешения и риски

1. **Паспорт хранит производные маркетинговые решения.** `project.positioning`, `positioningStatus`, `positioningFactIds`, `audiences`, `advantages` и обязательный `contentStrategy` смешивают исходные данные с интерпретацией и решением кампании. Эти поля нельзя удалять одномоментно: их нужно признать legacy/derived и мигрировать после проверки всех потребителей.
2. **`contentStrategy` обязательна в паспорте.** Это противоречит цели получать стратегию из исследования и паспортных данных. В целевой модели паспорт должен быть пригоден до того, как выбрана ЦА или CTA.
3. **`commercial` смешивает данные объекта и настройки KEY.** `leadWebhookEnvKey` и `crmPipeline` — интеграционная/операционная конфигурация, не характеристика ЖК. Они должны оставаться вне публичного runtime и в будущем жить в отдельном integration/deployment config.
4. **Дублируются способы хранить доказательства.** `evidencedValue`, `fact`, `infrastructureItem.source`, `apartmentPlan.sources` и источники в `marketContext` не имеют полностью единого контракта. Не следует переписывать их сразу, но целевой слой должен использовать общие source/evidence идентификаторы.
5. **Инфраструктура недостаточно нормализована.** Сейчас есть название, категория, дистанция/время и источник маршрута, но нет полноценной модели точки интереса: геопозиция, идентичность места, статус существования/работы, тип маршрута, профиль доступности и история проверки.
6. **Планировки не равны каталогу лотов.** Планировка — тип пространственного решения; лот — конкретная квартира с корпусом, секцией, этажом, площадью, ценой, статусом доступности и временем актуальности. Эти сущности нельзя смешивать.
7. **Активы описаны преимущественно как файлы.** Для автономного арт-дирекшена нужны назначение кадра, изображённая зона/объект, ракурс, стадия (рендер/фото/строительство), дата съёмки, соответствие объекту, права и разрешённые каналы/контексты.
8. **`marketContext` — правильный отдельный внутренний блок, но не доказательство спроса.** Рыночные объявления, цены конкурентов и число карточек нельзя интерпретировать как остатки, продажи или мотивы покупателей. Рыночные срезы должны сохранять выборку, дату, сопоставимость и ограничения.
9. **Нет единого понятия готовности данных по сценарию.** Общая полнота паспорта не должна блокировать страницу целиком. Готовность нужно рассчитывать по конкретному модулю, claim, интерактиву и режиму публикации.

### 2.3 Что фактически читает текущий runtime

Проверка `scripts/build-landing-runtime.mjs` показывает, что границы на уровне документации и фактического кода пока не совпадают полностью:

- runtime читает `passport.contentStrategy.modules` для выбора модулей и `passport.contentStrategy.visualDirection` для визуальной темы/композиции;
- runtime читает `passport.advantages`, `passport.infrastructure`, `passport.apartmentPlans`, `passport.assets`, `passport.offers` и `passport.facts`;
- утверждённый LANDING BRIEF используется для позиционирования, сегмента, hooks, CTA и связей с операционными offers; marketing JSON отдельно содержит обязательный copy;
- `marketContext` не читается runtime, что соответствует требованию внутренней изоляции;
- адаптер не получает Customer Experience JSON как отдельный вход и не проверяет его структурную/семантическую готовность;
- в текущем репозитории пока нет единой production-оркестрации, которая автоматически выполняет ingest → research → positioning → CX → brief → specification → build. Промпт описывает работу Strategist, а адаптер выполняет ограниченное преобразование уже подготовленных входов.

Следствие: нельзя заявлять, что текущая система уже автономно проходит всю цепочку. Сейчас реализованы отдельные контракты, промпты и проверяемый runtime-адаптер, но сквозная автономная оркестрация и readiness engine ещё являются целевыми задачами.

Дополнительное уточнение: текущая сущность `passport.offers` описывает исполнимые сценарии KEY (например, презентация, подбор, консультация, просмотр) и связывается с CTA из Landing Brief. Это не каталог коммерческих условий застройщика. Официальные цены, лоты, ипотечные программы, рассрочки и акции требуют отдельной предметной модели.

## 3. Целевые домены Project Passport

Паспорт должен быть базой проверяемых знаний об объекте, а не складом рекламных формулировок.

### A. Identity & parties — идентичность и участники
- стабильный ID проекта, название, тип/формат недвижимости;
- город, адрес, координаты, административный район;
- застройщик и юридическое лицо, проектные/строительные участники, управляющая организация — только когда известны;
- официальные идентификаторы объекта в государственных реестрах;
- связи проекта с корпусами/очередями и прежними/альтернативными названиями.

### B. Project & building characteristics — объект и здания
- класс/категория только с указанием основания и методики;
- корпуса, очереди, секции, этажность, подъезды;
- количество квартир и нежилых помещений;
- конструктив, фасады, материалы, инженерные системы;
- лифты, входные группы, лобби, доступность среды;
- двор, территория, озеленение, общественные зоны, сервисы;
- паркинг, кладовые, коммерческие помещения;
- акустические, экологические и иные параметры — только при наличии измерений/доказательств.

### C. Residential product — квартирный продукт
- типы планировок и их версии;
- комнаты, площадь, геометрия/план, высота потолка;
- корпус, секция, этаж и ориентация, если известны;
- отделка и комплектация с точным составом;
- особенности окон, балконов, лоджий, террас, видов;
- конкретные лоты — отдельная сущность, не синоним планировки;
- актуальность и история статусов лотов, цен и условий.

### D. Location & POI — локация и окружение
- географическая точка объекта;
- школы, детские сады, медицина, торговля, парки, спорт, транспорт и другие POI;
- идентификатор и координаты POI, тип и статус существования/работы;
- маршруты отдельно по способам передвижения;
- расстояние по прямой отдельно от маршрутного расстояния;
- расчётное время, дата, источник/метод и срок актуальности маршрута;
- доступность и ограничения маршрута, если они проверены.

### E. Construction & legal — строительство и документы
- разрешения, проектные декларации и их редакции;
- даты публикации/изменения, номера и сроки действия документов;
- плановые и фактические события строительства;
- фотоотчёты с датами съёмки и публикации;
- ввод, передача ключей и иные юридически значимые сроки как отдельные утверждения с источниками;
- история изменений характеристик проекта и расхождений источников.

### F. Commercial product data — коммерческие данные объекта
- официальные прайс-листы и история версий;
- конкретные лоты, цены и условия;
- программы оплаты, рассрочки, ипотечные условия, акции;
- сроки действия, ограничения, обязательные условия и источник;
- различие между официальным предложением, публичным объявлением посредника и рыночным наблюдением.

Этот домен не должен включать webhook, ключи окружения, CRM pipeline или секреты KEY.

### G. Asset & rights registry — материалы и права
- изображения, видео, планы, документы, карты, логотипы;
- роль материала: фасад, двор, лобби, интерьер, планировка, ход строительства и т. п.;
- тип представления: фото, рендер, схема, визуализация, документ;
- дата съёмки/создания/публикации, версия и соответствие проекту;
- автор/правообладатель, источник, подтверждение прав;
- допустимое публичное использование, каналы и ограничения;
- alt/описание, технические размеры/формат и связь с подтверждаемыми фактами.

### H. Market context — рыночные наблюдения
- конкурирующие объекты и критерии сопоставимости;
- публичные предложения, диапазоны и агрегированные показатели;
- период наблюдения, размер и состав выборки;
- метод сбора, источники, ограничения и надёжность;
- история срезов и изменение показателей;
- явное разделение предложения, спроса, сделок и рекламной активности.

Рыночный контекст внутренний. Публичное использование возможно только после отдельного анализа, проверки и обоснования конкретного утверждения.

## 4. Что должно жить вне паспорта

| Информация | Каноническое место | Почему |
|---|---|---|
| Мотивы, страхи, критерии, JTBD, сегменты, поведение | Customer Experience | Это знания о покупателях, а не свойства ЖК |
| Интервью, CRM-наблюдения, опросы и исследовательские выводы | Customer Experience evidence/research | Сохраняют метод, выборку и ограничения |
| Приоритетная ЦА, одна главная потребность и позиционирование кампании | Landing Brief | Один объект может иметь разные кампании |
| Hooks, рекламные сообщения, офферы KEY, воронки, CTA | Landing Brief | Это решения конкретной кампании |
| Состав, порядок и варианты модулей страницы | Landing Specification / manifest | Это результат проектирования страницы |
| Вебхуки, CRM pipeline, переменные окружения, секреты | Integration / deployment config | Это настройки KEY, не данные объекта |
| Персональные ответы посетителей и лиды | Lead/event storage с контролем доступа | Не должны попадать в публичный паспорт |

## 5. Единый контракт доказательств — целевое направление

Не вводить все поля одним большим объектом. Постепенно привести данные к общему принципу:

- **Entity** — к чему относится информация: проект, корпус, лот, POI, документ, актив, оффер.
- **Claim / observation** — что именно утверждается или наблюдается.
- **Value + unit** — нормализованное значение и единица измерения, где применимо.
- **Evidence** — откуда это известно: URL/документ/наблюдение, точное место/фрагмент, метод и дата доступа.
- **Validity** — период, на который значение применимо; дата следующей проверки для динамичных сведений.
- **Epistemic status** — подтверждено, предварительно, гипотеза, неизвестно, конфликт, устарело.
- **Publication policy** — разрешено, разрешено с оговоркой, только внутреннее, запрещено.
- **Limitations** — что источник не доказывает и какие выводы запрещены.
- **Lineage** — какие производные значения/решения построены на этом доказательстве.

Важно не сводить достоверность, свежесть и право публикации к одному статусу. Подтверждённый факт может устареть; актуальный источник может быть ненадёжным; достоверная внутренняя информация может быть запрещена к публикации.

Целевой подход — переиспользуемые source/evidence IDs и связи между сущностями, а не копирование одного и того же URL/текста в десятки полей. Текущие структуры остаются совместимыми до появления миграции и тестов всех потребителей.

## 6. Data Readiness — готовность не всего паспорта, а конкретного действия

Ввести вычисляемую оценку готовности по уровням:

1. **Research-ready:** достаточно исходных данных, чтобы изучать объект и формировать вопросы исследования.
2. **Strategy-ready:** есть достаточная база для выбора сегмента и позиционирования; гипотезы отделены от подтверждённых выводов.
3. **Module-ready:** конкретный модуль имеет нужные данные, активы, права и поведение.
4. **Claim-ready:** конкретная формулировка имеет допустимое доказательство, актуальность и разрешение на публикацию.
5. **Production-ready:** пройдены positioning gate, customer experience gate, legal/privacy, integration, responsive, accessibility и runtime QA.

Примеры:
- отсутствие цены не блокирует лендинг без ценового блока;
- отсутствие планировок блокирует показ планировок, но не обязательно страницу;
- отсутствие маршрута блокирует обещание времени пешком, но не факт существования POI;
- отсутствие интервью не превращает гипотезу о сегменте в факт и не должно блокировать безопасное исследование;
- отсутствие работающего обработчика блокирует production CTA, который обещает отправку заявки.

Каждый результат readiness должен содержать: статус, недостающие данные, затронутые модули/claims, риск, следующий способ устранения пробела и возможность безопасного обходного сценария.

## 7. Автономный pipeline

1. **Ingest:** сбор документов, страниц, файлов, структурированных источников.
2. **Extract:** извлечение кандидатов в факты, сущностей, активов и наблюдений.
3. **Normalize:** единицы, даты, география, идентификаторы, типы сущностей.
4. **Verify:** дедупликация, сопоставление источников, конфликты, права и актуальность.
5. **Enrich:** недостающие исследования рынка и покупателей с указанием метода/ограничений.
6. **Model customer experience:** сегменты, JTBD, барьеры, journey и proof needs.
7. **Strategize:** кампанийный фокус и Positioning Gate.
8. **Specify:** история страницы, модули, тексты, активы, CTA, интерактивы и события.
9. **Build & QA:** сборка, проверка фактов, модулей, UX, мобильных состояний и интеграций.
10. **Learn:** квалификация лидов, этапы воронки, результаты экспериментов и обновление знаний.

Автономность не означает право модели выдумывать отсутствующие данные или обходить gates. При недостатке сведений машина должна исследовать, маркировать неопределённость, исключать неподтверждённые claims или запрашивать проверку там, где риск нельзя безопасно обойти.

## 8. План эволюции без поломки текущей системы

### Этап 0 — зафиксировать границы
- утвердить этот документ как целевую архитектурную карту;
- не менять текущий schema contract;
- составить карту потребителей полей паспорта и их зависимостей.

### Этап 1 — аудит данных и качества
- проверить все поля паспорта на примере 905;
- классифицировать каждое поле: source fact, derived interpretation, campaign decision, integration config, legacy;
- найти дубли, пустые обязательные поля и значения без источников;
- проверить, какие данные реально читают adapter, prompts, tests и runtime.

### Этап 2 — нормализация доказательств
- согласовать единые source/evidence references;
- определить стабильные entity IDs и связи;
- добавить типы/единицы/validity только там, где есть реальный потребитель;
- сохранить обратную совместимость через адаптер/миграцию.

### Этап 3 — углубить объектные домены по приоритету
- POI и маршруты;
- корпуса/секции/планировки/лоты;
- документы и события строительства;
- активы и права;
- официальные коммерческие условия и история актуальности.

### Этап 4 — вычисляемая готовность
- описать требования данных для каждого модуля и claim;
- реализовать readiness report;
- тестировать, что пробел блокирует только зависимое действие, а не весь объект.

### Этап 5 — автономное обогащение и обучение
- автоматизировать сбор и извлечение;
- добавить исследовательские источники и evidence lineage;
- связать CRM/аналитику после появления поддерживаемого API и законного основания;
- замыкать цикл на квалифицированные обращения и коммерческие результаты.

## 9. Критерии успешной модели

Целевая модель считается полезной, если:

- один и тот же паспорт можно использовать для нескольких разных кампаний без перезаписи фактов;
- машина не путает факт, исследовательский вывод, гипотезу и маркетинговое решение;
- любое публичное существенное утверждение трассируется к допустимому доказательству;
- динамические сведения имеют дату актуальности и правила повторной проверки;
- планировка, лот и коммерческое предложение — разные сущности;
- POI и маршрут не смешиваются;
- права на медиа проверяются до публикации;
- внутренний рынок и служебные данные не попадают в публичный runtime;
- недостаток одного набора данных не блокирует независимые модули;
- система может объяснить, почему конкретный модуль/claim допущен или исключён;
- результат оценивается по качеству лидов и движению по воронке, а не по числу секций или сырых отправок.

## 10. Применение к паспорту КД «905»

КД «905» использовать как тестовый fixture для проверки универсальности, но не как источник архитектурных предположений.

В текущем паспорте уже есть полезные факты, инфраструктура, активы, планировки, рыночный контекст и пробелы. Следующий аудит должен определить, какие из этих записей:
- являются атомарными фактами;
- требуют обновления или первичного документа;
- являются внутренними рыночными наблюдениями;
- представляют маркетинговую интерпретацию;
- не имеют нужной детализации для будущего модуля.

Не добавлять в паспорт новые маркетинговые выводы по 905 без отдельной задачи. Его данные используются для проверки схемы и readiness, а не для преждевременного выбора ЦА или кампании.
