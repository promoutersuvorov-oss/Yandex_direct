# Спецификация модели данных KEY

## 1. Зачем нужен паспорт
Паспорт ЖК — единый контракт между исследовательским агентом, маркетинговым стратегом, сборщиком лендинга и QA. Он предотвращает потерю контекста при передаче между этапами и позволяет валидировать данные до генерации HTML.

## 2. Слои данных

| Слой | Что хранит | Можно выводить на сайт |
|---|---|---|
| `project` | Идентичность объекта, локация, характеристики | Только проверенные поля |
| `facts` | Атомарные утверждения с источниками и статусами | По `publicUse` и статусу |
| `advantages` | Польза для покупателя, привязанная к фактам | Да, если все supporting facts разрешены |
| `infrastructure` | Объекты окружения, расстояния, время пешком | Только при подтверждении маршрута/источника |
| `offers` | Сценарии CTA и lead magnet | Если сценарий реально реализован |
| `assets` | Рендеры, фото, планы, видео, документы | С учётом статуса и прав |
| `contentStrategy` | ONE CORE IDEA, CTA, решения по модулям, арт-дирекция | Влияет на генерацию, не является доказательством фактов |
| `commercial` | Вебхук, CRM, заметки брокера, закрытые условия | Никогда автоматически |
| `verification` | Дата проверки, конфликты, пробелы, ручные проверки | Внутренний QA |

## 3. Правило атомарности
Одна запись `facts[]` должна выражать одно проверяемое утверждение. Например, «рядом есть школа и парк» — две записи, а не одна. Это позволяет одному факту быть подтверждённым, а другому — нет.

## 4. Разделение факта и маркетингового смысла
Факт: «парк находится в 500 м по пешеходному маршруту» — при наличии источника.
Интерпретация: «можно выйти на прогулку после работы».
Hook: «Парк — часть вашего привычного маршрута домой».
Последние два слоя допустимы только если не создают ложного обещания и соответствуют подтверждённому факту.

## 5. Правила для динамических данных
Цена, доступность квартир, ипотечные программы, сроки сдачи и статус строительства имеют дату проверки. Если дата устарела или источник недоступен, соответствующий блок должен скрываться, показывать нейтральный запрос актуальных условий либо переходить на ручную проверку — но не сохранять старые цифры как актуальные.

## 6. Контракт модулей
Каждое решение по модулю содержит:
- `moduleId` — идентификатор из `MODULE_LIBRARY.md`;
- `decision` — include / exclude / conditional / replace;
- `reason` — объяснение на основе объекта и сценария;
- `requiredFactIds` — обязательные подтверждённые факты;
- `variant` — конкретный вариант визуальной/контентной реализации.

Модуль нельзя включать, если его обязательные факты отсутствуют, конфликтуют или заблокированы. Условный модуль должен иметь fallback.

## 7. Следующий этап
1. Прочитать реальные `MODULE_LIBRARY.md`, `project-config.k15.js`, `content-config.k15.js`.
2. Сопоставить поля существующих конфигураций со схемой.
3. Составить таблицу миграции: `legacy field → canonical field → transform → validation`.
4. Не менять рабочий эталон до появления проверяемого адаптера и regression checklist.
5. После миграции собрать паспорт K15 только из фактов с источниками и запустить QA.
