# KEY LANDING SYSTEM — FOUNDATION SPECIFICATION v1.0

**Статус:** проектная спецификация для MVP шаблона KEY  
**Основа:** master lending.md и аудит структуры K15_лендинг_v27.1  
**Цель этапа:** превратить текущий лендинг K15 в управляемый эталон и основу для сборки лендингов других ЖК.  
**Не входит в текущий этап:** проверка готовности к запуску, настройка реальных CRM-вебхуков, production-интеграции и финальный аудит передачи лидов. Эти проверки проводятся после того, как сформирован устойчивый MVP.

---

## 1. Принципы продукта KEY

1. **Лендинг — инструмент привлечения лида, а не энциклопедия ЖК.** Он должен вызывать интерес, показывать ценность проекта и мотивировать на следующий шаг с KEY.
2. **Визуальная подача премиальная и осмысленная.** Не использовать безликие секции, декоративные эффекты ради эффектов и шаблонный «нейросетевой» стиль.
3. **Маркетинговые крючки — сильные, но проверяемые.** Не придумывать характеристики, цены, сроки, наличие квартир, расстояния или условия покупки.
4. **У каждого интерактивного элемента есть понятная функция.** Кнопки не должны вести в одну и ту же форму, если пользователь ожидает разные действия.
5. **Один мастер-шаблон — разные конфигурации.** Новый ЖК собирается настройкой данных, структуры, контента и визуальных вариантов, а не переписыванием страницы с нуля.
6. **Не показывать пустые и сломанные данные.** Если факт отсутствует, компонент должен скрыть значение, показать нейтральный fallback или запросить уточнение — согласно своему контракту.
7. **Не смешивать факты и рекламные формулировки.** Для значимых утверждений хранить источник, дату проверки и статус подтверждения.
8. **Сначала стратегия, затем сборка.** Сначала определить аудиторию, позиционирование, доказуемые преимущества и сценарии конверсии; затем выбирать секции и визуальные варианты.

---

## 2. Архитектура системы

Система разделяется на пять уровней:

1. **PROJECT DATA** — структурированные факты о ЖК: название, адрес, характеристики, цены, сроки, инфраструктура, планировки, документы, изображения и источники.
2. **MARKETING STRATEGY** — аудитории, позиционирование, преимущества, hooks, возражения и сценарии конверсии.
3. **PAGE CONFIG** — порядок секций, включение/выключение, варианты компоновки, тексты и настройки интерактивности.
4. **KEY MASTER TEMPLATE** — дизайн-токены, библиотека компонентов, адаптивное поведение, состояния, действия и правила доступности.
5. **ASSEMBLED PAGE + QA** — собранная страница и проверки контента, визуальной целостности, адаптивности, интерактивных сценариев и переносимости на другой ЖК.

```text
PROJECT DATA ─┐
               ├─> MARKETING STRATEGY ─> PAGE CONFIG ─> KEY MASTER TEMPLATE
SOURCES ───────┘                                        │
                                                       ▼
                                              ASSEMBLED LANDING
                                                       │
                                                       ▼
                                                 QA / ITERATION
```

**Правило:** компонент не должен самостоятельно придумывать недостающие данные. Стратегия может выбрать акцент из подтверждённых фактов, но не менять факт.

# PART A. PROJECT_SCHEMA

## 3. Назначение

`PROJECT_SCHEMA` — единый источник данных о конкретном ЖК. Компоненты получают данные из схемы, а не извлекают факты из текста страницы и не хранят их в разметке.

Схема ниже — целевая модель v1. Некоторые поля могут отсутствовать. Отсутствие поля не должно ломать страницу.

## 4. Базовая структура данных

```json
{
  "schemaVersion": "1.0",
  "project": {
    "id": "k15",
    "name": "K15",
    "slug": "k15",
    "city": null,
    "address": null,
    "coordinates": null,
    "projectType": null,
    "positioning": null
  },
  "developer": {
    "name": null,
    "description": null,
    "officialUrl": null,
    "documents": []
  },
  "keyFacts": [],
  "pricing": {
    "currency": "RUB",
    "startingPrice": null,
    "startingMonthlyPayment": null,
    "paymentPrograms": [],
    "lastVerifiedAt": null
  },
  "delivery": {
    "status": null,
    "completionDate": null,
    "handoverDate": null
  },
  "features": [],
  "infrastructure": [],
  "gallery": [],
  "apartmentPlans": {
    "mode": "demo",
    "items": [],
    "availabilitySource": null,
    "lastVerifiedAt": null
  },
  "mortgage": {
    "calculatorMode": "estimate",
    "programs": [],
    "disclaimer": null
  },
  "faq": [],
  "sources": [],
  "leadScenarios": [],
  "assets": {},
  "metadata": {
    "createdAt": null,
    "updatedAt": null,
    "contentOwner": null
  }
}
```

Значения `null` в этом примере — намеренно незаполненные поля, а не утверждение, что у K15 отсутствуют соответствующие характеристики. Перед использованием конкретного проекта поля должны быть заполнены подтверждёнными данными либо оставлены пустыми.

## 5. Сущности и поля

### 5.1 Project

| Поле | Тип | Правило |
|---|---|---|
| `id` | string | Стабильный машинный идентификатор |
| `name` | string | Отображаемое название |
| `slug` | string | URL-идентификатор |
| `city` | string/null | Не выводить, если неизвестно |
| `address` | string/null | Не подменять районом или ориентиром |
| `coordinates` | `{lat, lon}`/null | Только из подтверждённого источника |
| `projectType` | enum/string/null | Например, клубный дом — только если подтверждено |
| `positioning` | string/null | Краткое позиционирование, сформированное из фактов |

### 5.2 Facts / Features

Каждый значимый факт хранится отдельно от рекламного текста:

```json
{
  "id": "private-territory",
  "label": "Закрытая территория",
  "value": true,
  "unit": null,
  "status": "verified",
  "sourceIds": ["source-001"],
  "verifiedAt": "YYYY-MM-DD",
  "notes": null
}
```

Допустимые статусы:
- `verified` — подтверждён источником;
- `needs_review` — найдено, но требуется проверка;
- `unverified` — пока нет достаточного подтверждения;
- `conflicting` — источники противоречат друг другу;
- `not_available` — известно, что характеристики нет;
- `unknown` — данных недостаточно.

Правила:
- Только `verified` можно подавать как безусловный факт.
- `needs_review`, `unverified` и `conflicting` не должны попадать в публичные категоричные заявления.
- `not_available` отличается от `unknown`: «нет» не равно «неизвестно».
- Для чисел обязательны единицы измерения и понятная семантика: расстояние по маршруту или по прямой, цена за квартиру или за м² и т. п.

### 5.3 Sources

```json
{
  "id": "source-001",
  "url": "https://example.com",
  "title": null,
  "publisher": null,
  "sourceType": "developer",
  "accessedAt": "YYYY-MM-DD",
  "supports": ["private-territory"],
  "quoteOrEvidence": null,
  "reliability": "primary"
}
```

`example.com` — демонстрационный placeholder. В рабочем объекте он должен быть заменён реальным источником.

Рекомендуемые `sourceType`: `developer`, `official_document`, `official_project_page`, `trusted_listing`, `map`, `other`. Источник не считается подтверждением автоматически: нужно убедиться, что он действительно поддерживает конкретное утверждение.

### 5.4 Infrastructure

```json
{
  "id": "park-001",
  "name": null,
  "category": "park",
  "distanceMeters": null,
  "distanceType": "walking_route",
  "walkingMinutes": null,
  "sourceIds": [],
  "status": "needs_review"
}
```

Нельзя рассчитывать и публиковать точное время пешком только из расстояния по прямой. Если расстояние или время не подтверждены, можно использовать нейтральную формулировку без точной цифры либо не показывать карточку.

### 5.5 Pricing and delivery

Цена и сроки — динамические данные. Для них обязательно хранить дату проверки и источник. Не выводить формулировки вроде «от млн ₽», «платёж от ₽/мес.» или пустое поле «Срок сдачи:».

```json
{
  "value": null,
  "currency": "RUB",
  "unit": "apartment",
  "sourceIds": [],
  "verifiedAt": null,
  "status": "unknown"
}
```

Показывать цену или платёж только если значение и единица понятны, статус допускает публичный показ, а обязательные условия/дисклеймеры доступны. Если данных нет — скрыть числовой блок и использовать CTA «Уточнить актуальные условия», если это соответствует сценарию.

### 5.6 Apartment plans

Планировка должна явно иметь режим:
- `demo` — демонстрационный пример; нельзя создавать впечатление, что квартира доступна к покупке;
- `catalog` — список типов планировок, без гарантии текущего наличия;
- `live_availability` — актуальное наличие только при подключённом и проверенном источнике данных.

Каждый объект планировки должен хранить только подтверждённые характеристики. Площадь, количество комнат, цена, этаж и статус наличия не должны выводиться, если они не подтверждены для этой планировки.

### 5.7 Mortgage

Калькулятор должен различать:
- `estimate` — приблизительный сценарный расчёт;
- `program_based` — расчёт по введённым условиям программы, которые нужно проверять;
- `live_offer` — только при наличии актуального источника/интеграции.

Для MVP допускается `estimate`, но интерфейс должен явно объяснять, что это ориентировочный расчёт, а не одобрение банка и не гарантированная ставка. Формула и входные параметры должны быть единообразными, а не зашитыми в разные секции страницы.

### 5.8 Lead scenarios

Сценарии заявки описываются семантически:

```json
{
  "id": "request-presentation",
  "intent": "presentation",
  "title": "Получить презентацию",
  "description": null,
  "formVariant": "contact",
  "successMessage": "Запрос принят",
  "fields": ["name", "phone"],
  "contextFields": ["projectId", "sourceSection", "utm"],
  "enabled": true
}
```

Текст успеха здесь — пример для макета, а не подтверждение реального получения заявки. На этапе MVP нужно проверять пользовательский сценарий и UI; реальную доставку в CRM — отдельно на этапе интеграций.

# PART B. SECTION_SCHEMA

## 6. Зачем нужна конфигурация секций

Секция — это конфигурируемая часть страницы, а не отдельный фрагмент, который приходится вручную копировать и менять в HTML. Для каждого проекта можно:
- включать или отключать секцию;
- менять порядок;
- выбирать допустимый вариант композиции;
- задавать контент и CTA;
- указывать условия показа;
- задавать поведение на мобильных устройствах.

## 7. Формат секции

```json
{
  "id": "hero",
  "type": "hero",
  "enabled": true,
  "order": 10,
  "variant": "editorial",
  "content": {
    "eyebrow": null,
    "headline": null,
    "subheadline": null,
    "imageIds": [],
    "proofPointIds": []
  },
  "actions": [
    {
      "label": "Получить презентацию",
      "scenarioId": "request-presentation",
      "style": "primary"
    }
  ],
  "visibility": {
    "requires": [],
    "hideWhenMissing": []
  },
  "responsive": {
    "mobileVariant": "stacked",
    "mediaPriority": "high"
  }
}
```

`variant` — это ключ к заранее разработанному и проверенному варианту компонента. Это не свободный промпт, который генерирует новую композицию каждый раз.

## 8. Каталог секций v1 для K15

Ниже — исходный каталог по фактически обнаруженной структуре K15. Он не означает, что все секции обязаны присутствовать на каждом новом ЖК.

| ID | Назначение | Возможные правила |
|---|---|---|
| `hero` | Первое впечатление и главный CTA | Обязательна; нужен подтверждённый визуальный материал |
| `key` | Ключевые характеристики | Скрывать отсутствующие факты |
| `gallery` | Атмосфера и визуальные доказательства | Нужны качественные изображения |
| `about` | Концепция дома и образ жизни | Не дублировать Hero |
| `security` | Территория и безопасность | Показывать только подтверждённые характеристики |
| `parking` | Парковка | Скрыть, если тип и условия не подтверждены |
| `quiz` | Квалификация интереса | Не обязательна; должна иметь ясную пользу и сценарий |
| `location` | Локация и инфраструктура | Только проверенные места и расстояния |
| `lifestyle` | Сервисы и образ жизни | Не смешивать планируемое и действующее |
| `gift` | Лид-магнит | Только если материал реально подготовлен |
| `apartments` | Планировки/изучение квартир | Ясно обозначать demo/catalog/live режим |
| `price` | Цена и платёж | Не показывать пустые/устаревшие числа |
| `developer` | Застройщик и документы | Указывать только подтверждённые данные |
| `steps` | Следующие шаги покупки | Не обещать процесс, который KEY не контролирует |
| `mortgage` | Ориентировочный расчёт ипотеки | Дисклеймер; согласованные параметры расчёта |
| `faq` | Снятие возражений | Ответы должны опираться на подтверждённые факты |
| `contacts` | Финальный контакт | Сценарий должен соответствовать CTA |

## 9. Правила выбора структуры

Структура выбирается на основании:
1. типа проекта и его реальных отличий;
2. целевой аудитории и её мотивации;
3. наличия качественных визуальных материалов;
4. подтверждённых фактов и ограничений;
5. главного сценария конверсии;
6. длины и сложности пути принятия решения.

Правила:
- Не добавлять секцию только потому, что она есть в эталоне.
- Не удалять сильный подтверждённый аргумент только ради сокращения страницы.
- Не повторять один тезис в Hero, About, Key Facts и FAQ без новой функции.
- Секции должны образовывать историю: **интерес → ценность → доказательства → выбор следующего шага → заявка**.
- Порядок должен быть осмысленным; не использовать одну фиксированную последовательность как закон для любого ЖК.

## 10. Предлагаемая логика страницы

Базовый вариант, который затем адаптируется под конкретный ЖК:

1. Hero — позиционирование + основной CTA.
2. Key facts — короткие факты, поддерживающие обещание.
3. Gallery / концепция — эмоциональное погружение.
4. Уникальные преимущества — только самые сильные и доказуемые.
5. Локация — инфраструктура, если это значимо для аудитории.
6. Apartment explorer — изучение планировок с прозрачным режимом данных.
7. Цена / ипотека — только если данные достаточны и актуальны.
8. FAQ — ответы на ключевые возражения.
9. Финальный CTA — следующий шаг с KEY.

Это не жёсткая последовательность. Секции `parking`, `security`, `lifestyle`, `gift`, `quiz`, `developer`, `steps` включаются, когда они усиливают историю и соответствуют данным проекта.

# PART C. COMPONENT_CONTRACTS

## 11. Общий контракт компонента

Каждый переиспользуемый компонент должен описывать:

- **Purpose:** какую задачу пользователя решает.
- **Inputs:** какие данные принимает и какие обязательны.
- **Variants:** какие заранее проверенные композиции поддерживает.
- **States:** normal, loading, empty, error, disabled и другие специфические состояния.
- **Actions:** что делает каждый интерактивный элемент.
- **Rules:** что запрещено, какие данные скрываются и как обрабатываются отсутствующие значения.
- **Responsive behavior:** поведение на мобильном, планшете и широком экране.
- **Analytics events:** семантические события, которые можно подключить на следующем этапе.
- **Acceptance criteria:** проверяемые условия готовности компонента.

## 12. Контракты ключевых компонентов

### 12.1 Hero

**Purpose:** за несколько секунд объяснить характер проекта и дать привлекательный следующий шаг.

**Inputs:** headline, subheadline, hero media, подтверждённые proof points, primary CTA, optional secondary CTA.

**Variants v1:** `editorial`, `full_bleed`, `split_layout`. Не все варианты обязаны быть доступны для каждого набора материалов.

**States:** normal; media fallback; reduced-motion.

**Rules:**
- Не использовать неподтверждённые суперлативы («лучший», «самый престижный»).
- Не показывать пустые proof points.
- Главный CTA должен соответствовать обещанному действию.
- Изображение не должно ломать композицию на узких экранах.

**Acceptance:** заголовок читается без наложений; CTA виден; мобильный Hero выглядит как спроектированная версия, а не случайно сжатый desktop.

### 12.2 Key Facts

**Purpose:** быстро передать 3–6 наиболее значимых подтверждённых характеристик.

**Inputs:** массив facts с источниками и статусами.

**Rules:** выводить только факты со статусом `verified`; единицы и подписи обязательны для количественных значений; скрывать пустые карточки; не дублировать одинаковые факты в соседних секциях без причины.

**Acceptance:** нет пустых чисел, неверных единиц и карточек-заглушек.

### 12.3 Gallery / Story Gallery

**Purpose:** не просто показать картинки, а поддержать последовательный эмоциональный рассказ.

**Inputs:** image IDs, alt text, captions (optional), ordering, focal point.

**Variants v1:** `masonry_editorial`, `horizontal_story`, `large_split`.

**Rules:** не генерировать несуществующие виды/интерьеры как будто это реальные фото объекта; рендеры при необходимости обозначать как визуализации; не обрезать критически важные детали.

**Acceptance:** единый визуальный ритм, предсказуемая обрезка, управление на touch-экранах.

### 12.4 Feature Story

Используется для преимуществ вроде территории, парковки, сервиса, Smart Home или других характеристик, если они подтверждены.

**Inputs:** title, description, fact IDs, media, CTA optional.

**Rules:** каждое преимущество должно отвечать на вопрос «что это меняет для жителя?» и иметь фактическое основание. Не создавать секцию, если доказательства отсутствуют.

### 12.5 Infrastructure

**Purpose:** показать значимые места вокруг проекта и помочь оценить повседневный маршрут.

**Inputs:** place name, category, verified distance/duration, source, optional map link.

**Rules:** не смешивать расстояние по прямой с пешим маршрутом; не придумывать время пути; указывать понятный контекст расстояния. Не превращать карту в перегруженный каталог.

**Acceptance:** у каждой цифры есть источник и тип измерения; мобильная версия остаётся читаемой.

### 12.6 Apartment Explorer

**Purpose:** дать пользователю интерактивно изучить варианты планировок и выбрать следующий шаг.

**Inputs:** plans/media, confirmed room count and area when available, data mode, CTA scenario.

**States:** `3d_view`, `blueprint_view`, `filter_selected`, `empty`, `loading`, `error`.

**Actions:** переключить визуализацию; выбрать число комнат/тип; открыть подробности, если они реально доступны; запросить подборку/планировки.

**Rules:**
- Ясно отличать демонстрационную планировку от доступной к покупке квартиры.
- Не показывать фильтры, для которых нет данных.
- Не выводить наличие в реальном времени без актуального источника.
- Не подменять точную геометрию планировки декоративной визуализацией.
- На мобильном элементы управления не должны перекрывать план.

**Acceptance:** каждый переключатель действительно меняет состояние; пустой набор данных обрабатывается; CTA сохраняет контекст выбранного типа, если он есть.

### 12.7 Price & Mortgage Calculator

**Purpose:** помочь ориентироваться в финансовом сценарии, не выдавая оценку за предложение банка.

**Inputs:** confirmed starting price (optional), down payment, term, rate or explicitly selected estimate assumptions, currency, disclaimer.

**States:** incomplete inputs, calculated estimate, invalid inputs, missing price.

**Actions:** изменить входные значения; пересчитать результат; запросить уточнение условий.

**Rules:**
- Не показывать `0 ₽`, если данных нет.
- Формула расчёта едина во всех местах лендинга.
- Ставка и условия должны быть явно обозначены как введённые пользователем, ориентировочные или подтверждённые.
- Не заявлять «самая выгодная ипотека» без доказуемого сравнения.
- Ориентировочный платёж не равен банковскому одобрению.

**Acceptance:** одинаковые параметры дают одинаковый результат; ошибки ввода объясняются; пустые значения не выглядят как реальные предложения.

### 12.8 Quiz

**Purpose:** помочь пользователю сформулировать потребность и создать релевантный повод для контакта.

**Inputs:** questions, answer options, outcome mapping, CTA scenario.

**States:** initial, question answered, back navigation, completed.

**Rules:** каждый вопрос влияет на результат или контекст обращения; не собирать лишние персональные данные до понятного объяснения; можно вернуться назад; CTA отражает реальный результат квиза.

**Acceptance:** все варианты ответов работают; состояние не теряется неожиданно; результат соответствует ответам.

### 12.9 Lead Modal / Form

**Purpose:** выполнить конкретное намерение: презентация, просмотр, подбор планировок, ипотека, вопрос.

**Inputs:** scenario ID, fields, project ID, source section, optional selected plan/quiz context.

**Rules:**
- Разные намерения могут иметь разные заголовки, поля, пояснения и success states.
- Не вести все CTA в визуально одинаковую форму, если это противоречит обещанию кнопки.
- Перед отправкой понятно объяснить, что произойдёт после заявки.
- Успешный экран не должен утверждать, что CRM получила лид, пока это не подтверждено реальным интеграционным тестом.

**Acceptance:** заголовок формы соответствует CTA; выбранный контекст сохраняется; обязательные поля валидируются; доступно закрытие и возврат к странице.

### 12.10 FAQ

**Purpose:** снимать существенные возражения, не раскрывая лишние детали и не создавая недостоверных обещаний.

**Inputs:** question, answer, source IDs, status, optional CTA.

**Rules:** не публиковать ответы с неподтверждёнными ценами, сроками и условиями; если точный ответ зависит от ситуации, направить к эксперту без имитации определённости.

### 12.11 CTA / Action Button

**Purpose:** обеспечить ясный и предсказуемый следующий шаг.

**Inputs:** label, intent, scenario ID, visual style, context.

**Rules:** текст кнопки описывает действие; `scenarioId` обязателен для кнопок, ведущих в сценарий; не использовать одинаковую обработку для разных намерений без явного решения продукта.

**Acceptance:** клик меняет интерфейс ожидаемым образом; клавиатурное управление и закрытие доступны; событие имеет семантическое имя для будущей аналитики.

# PART D. DESIGN SYSTEM И КОНТРОЛИРУЕМАЯ ВАРИАТИВНОСТЬ

## 13. Что должно быть централизовано

В дизайн-системе централизуются:
- цветовые токены;
- типографическая шкала;
- размеры контейнеров и отступы;
- сетка и брейкпоинты;
- радиусы, границы и тени;
- состояния кнопок, полей, карточек и модальных окон;
- правила анимации и reduced motion;
- фокус, контраст и доступность.

Не нужно задавать каждый отступ произвольно внутри каждой секции. Но не нужно и делать весь лендинг визуально одинаковым: вариативность создаётся через утверждённые композиции, ритм, изображения, масштаб типографики и порядок секций.

## 14. Принципы премиального UI

- Выразительная типографика и управляемая ширина текстовых строк.
- Сильная работа с изображениями, а не случайные декоративные градиенты.
- Контраст между крупными визуальными секциями и спокойными информационными блоками.
- Единая система кнопок и интерактивных состояний.
- Пустое пространство — намеренный инструмент композиции, а не незаполненная область.
- Микроанимации только там, где они помогают понять действие или создают уместный акцент.
- Desktop и mobile проектируются как связанные, но разные композиции.
- Не более одного очевидного главного действия на одном экране; вторичные действия визуально слабее, но доступны.

# PART E. QA И КРИТЕРИИ ЭТАЛОНА

## 15. QA-гейты

### Gate 1 — Data integrity
- Нет пустых динамических чисел и оборванных фраз.
- Нет неподтверждённых характеристик, цен, сроков, расстояний.
- Каждое значимое утверждение имеет статус и источник.
- Demo/catalog/live availability явно различаются.

### Gate 2 — Content & marketing
- Понятно, для кого проект и почему он может быть интересен.
- У каждого ключевого преимущества есть фактическая основа.
- Секции не повторяют один и тот же тезис без новой функции.
- Есть понятный путь к следующему шагу с KEY.

### Gate 3 — Visual
- Нет горизонтального переполнения, наложений и случайных пустых областей.
- Текст не обрезается и не распадается на неудобные строки.
- Изображения не ломают ритм и не скрывают важные детали.
- Модальные окна, фильтры и калькулятор читаемы на мобильном.
- Анимации не мешают чтению и управлению.

### Gate 4 — Interaction
- Каждый CTA ведёт в соответствующий сценарий.
- Все фильтры, переключатели и шаги квиза реально меняют состояние.
- Закрытие/возврат работает.
- Есть пустые, ошибочные и незаполненные состояния.
- Формы сохраняют контекст намерения пользователя.

### Gate 5 — Reusability
- Новый ЖК можно собрать через данные и конфигурацию.
- Секции можно менять местами, отключать и выбирать варианты без копирования всей страницы.
- Отсутствие конкретной функции у другого ЖК не ломает макет.
- Визуальная вариативность ограничена проверенными вариантами, а не случайной генерацией.

### Gate 6 — Second-project portability
- Выбрать другой ЖК с отличающимся позиционированием/набором характеристик.
- Заполнить только PROJECT DATA, MARKETING STRATEGY и PAGE CONFIG.
- Не менять ядро мастер-шаблона ради обычного отличия проекта.
- Зафиксировать исключения, которые действительно требуют нового компонента.

## 16. Definition of Done для MVP шаблона

Система считается готовой к следующему этапу, когда:

- [ ] Данные ЖК вынесены из HTML/JS-компонентов в отдельную схему.
- [ ] Для секций существует конфигурация включения, порядка и варианта.
- [ ] У ключевых компонентов описаны входы, состояния, действия и fallback.
- [ ] Значимые утверждения связаны с источниками и статусами проверки.
- [ ] Динамические поля не отображаются пустыми.
- [ ] У CTA есть различимые сценарии и предсказуемые действия.
- [ ] Визуальная система едина, но допускает управляемую вариативность.
- [ ] Ключевые интерактивные компоненты работают на мобильном.
- [ ] Есть QA-чек-лист и повторяемый процесс проверки.
- [ ] Второй ЖК собран без переписывания ядра шаблона.

**Важно:** проверка реальной CRM-доставки, webhook, UTM, фактического сохранения ответов и мониторинга событий — отдельный этап после стабилизации MVP, а не критерий завершения этой архитектурной спецификации.

# PART F. ПЛАН ВНЕДРЕНИЯ В K15

## 17. Рекомендуемый порядок работ

### Этап 1 — Зафиксировать текущий эталон
1. Сохранить текущую версию K15 как baseline.
2. Составить список всех секций, CTA, модальных окон, переключателей, фильтров и калькуляторов.
3. Для каждого интерактивного элемента записать ожидаемое действие и фактическое поведение.
4. Отдельно отметить известные дефекты данных: пустая цена, пустой платёж, пустой срок сдачи и аналогичные поля.

### Этап 2 — Вынести данные
1. Создать `project.k15.json` по PROJECT_SCHEMA.
2. Перенести факты и контент из разметки в объект данных.
3. Для каждого важного факта добавить источник, статус и дату проверки.
4. Не заполнять неизвестное догадками.
5. Подключить компоненты к схеме и проверить отсутствие визуальных регрессий.

### Этап 3 — Конфигурация секций
1. Создать `page.k15.json` по SECTION_SCHEMA.
2. Перенести порядок секций, варианты и CTA в конфигурацию.
3. Реализовать правила скрытия пустых блоков.
4. Проверить возможность отключить необязательную секцию без поломки страницы.

### Этап 4 — Контракты и библиотека компонентов
1. Начать с Hero, Key Facts, CTA/Modal, Apartment Explorer, Price/Mortgage.
2. Зафиксировать состояния и сценарии.
3. Избавиться от повторяющейся логики в разных секциях.
4. Создать визуальные варианты только там, где есть реальная потребность.

### Этап 5 — Калибровка эталона
1. Проверить desktop и mobile.
2. Проверить композицию, ритм, типографику, пустые состояния и интерактивность.
3. Убрать дублирование смыслов и CTA с неожиданным поведением.
4. Провести QA-гейты 1–5.

### Этап 6 — Тест переносимости
1. Выбрать второй ЖК с отличающимися характеристиками.
2. Подготовить его PROJECT DATA, MARKETING STRATEGY и PAGE CONFIG.
3. Собрать лендинг на той же библиотеке.
4. Изменения ядра разрешать только при доказанном пробеле в системе, а не ради разового дизайна.

### Этап 7 — Отдельный этап перед запуском
После стабилизации MVP отдельно проверить:
- реальные CRM/webhook-передачи;
- сохранение источников и UTM;
- передачу ответов квиза и выбранной планировки;
- обработку ошибок интеграций;
- аналитику и мониторинг.

Этот этап сознательно отложен до готовности MVP.

## 18. Первый приоритет для K15

Начать не с полного переписывания страницы, а с трёх артефактов в кодовой базе:

1. `schemas/project.schema.json` — формальная схема данных проекта;
2. `config/project.k15.json` и `config/page.k15.json` — данные и конфигурация K15;
3. `docs/component-contracts.md` — контракты компонентов и состояний.

После этого переносить данные и поведение постепенно, сохраняя рабочий baseline и проверяя визуальные регрессии на каждом шаге.

## 19. Ограничения этой версии

- Это фундаментальная продуктовая/архитектурная спецификация, а не подтверждение того, что текущий HTML уже соответствует ей.
- Пример JSON содержит placeholders и должен быть заполнен данными K15 после сверки с актуальными источниками.
- Перечень секций отражает обнаруженную структуру K15; он не делает каждую секцию обязательной для всех будущих ЖК.
- Интерактивность описана как требуемое поведение; реальная работоспособность каждого сценария должна быть подтверждена отдельным тестом.
- Перед реализацией нужно согласовать стек и структуру репозитория, чтобы не навязать неподходящий способ сборки.
