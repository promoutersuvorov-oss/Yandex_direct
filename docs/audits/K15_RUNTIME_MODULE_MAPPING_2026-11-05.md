# K15: сопоставление каталога модулей с фактическим HTML runtime

**Дата:** 2026-11-05  
**Источник:** `landing/reference/K15_landing_edited.html`, статический разбор исходника.  
**Назначение:** зафиксировать, какие смысловые модули уже представлены в K15 HTML, а какие отсутствуют или объединены. Это не подтверждение браузерного поведения и не доказательство, что генератор умеет динамически собирать их.

## 1. Главный вывод

В K15 обнаружены 16 статически размеченных секций:

`hero → key → gallery → about → security → quiz → location → lifestyle → gift → apartments → price → developer → steps → mortgage → faq → contacts`.

Это полезная база компонентов и контентных паттернов. Однако текущий HTML не содержит обнаруженных контрактов `sectionManifest`, `moduleManifest`, `data-module`, `sectionOrder` или `enabledSections`. Порядок секций зафиксирован разметкой.

**Следствие:** K15 можно использовать как reference renderer и источник паттернов, но нельзя утверждать, что текущий K15 уже является универсальным движком с динамической композицией секций.

## 2. Карта соответствия

| Каталог moduleId | Фактическая секция / элемент K15 | Статус соответствия | Примечание |
|---|---|---|---|
| `hero` | `#hero` | Есть | Первый экран |
| `key-facts` | `#key` | Есть, имя отличается | Ключевые характеристики |
| `architecture` | `#about` | Частично | Концепция/характер дома; не отдельная архитектурная история во всех возможных вариантах |

| `privacy-security` | `#security` | Есть | Закрытая территория и контроль доступа |
| `parking` | Отдельной секции нет; есть ключ `parking` в конфигурации модальных сценариев | Только CTA/диалоговая заготовка | Не считать полноценным модулем паркинга |
| `location` | `#location` | Есть | Локация и маршруты |
| `infrastructure` | Встроено в `#location` | Частично / объединено | Инфраструктура не является отдельной секцией |

| `interiors` | Внутри `#apartments` / медиа | Частично | Интерьерная визуализация должна быть отличима от технического плана |
| `price` | `#price` | Есть | Цена и финансовые сообщения; динамические значения требуют проверки |

| `mortgage` | `#mortgage` | Есть | В текущем HTML есть ипотечный сценарий/CTA; наличие полноценного расчётного инструмента проверяется отдельно |
| `developer` | `#developer` | Есть | Застройщик и документы |
| `construction-progress` | Отдельной секции нет | Нет | Нельзя выводить из наличия документов или статуса строительства |
| `documents` | Документы внутри `#developer` | Частично / объединено | Не отдельная секция |
| `offer` | Предложения внутри `#price` и `#gift` | Частично / объединено | Сроки и условия каждого оффера должны быть проверены |
| `lead-magnet` | `#gift` | Есть как сценарий | Наличие файла/реальной выдачи требует отдельной проверки |
| `quiz` | `#quiz` | Есть | Трёхшаговый квиз |
| `faq` | `#faq` | Есть | FAQ |
| `process` | `#steps` | Есть | Этапы после обращения |
| `contacts` | `#contacts` | Есть | Контактный сценарий |
| `final-cta` | Отдельной секции нет; CTA распределены по странице | Нет отдельной секции | Финальное действие можно реализовать внутри contacts/другого модуля |
| `footer` | Семантический footer, не отдельная `section` | Частично | Требует отдельного аудита ссылок/юридической информации |
| `modal` | `#modal` и объект `MODALS` | Есть | 12 ключей сценариев в объекте; 7 уникальных `data-modal` значений найдены в статической разметке |
| `lightbox` | Галерея / просмотр медиа | Есть как поведение | Нужна отдельная проверка доступности и управления |
| `map` | Встроено в `#location` | Есть как часть секции | Геоданные и провайдеры должны быть подтверждены |

## 3. Выводы по модульной архитектуре

1. Один DOM section может обслуживать несколько смысловых moduleId (например, `#apartments` объединяет apartments, floor-plans и часть interiors).
2. Наличие одного moduleId в каталоге не требует создавать отдельную секцию, если объединённый блок решает вопросы пользователя без потери ясности.
3. Система должна отличать `moduleId` от `sectionId`: первый описывает пользовательскую задачу, второй — конкретный DOM/runtime контейнер.
4. Для объединённых модулей нужно явно задавать mapping и порядок внутренних подблоков.
5. Для отсутствующего модуля генератор должен выбирать supported alternative, `conditional` или `not_implemented`, но не рисовать пустой блок.
6. Нельзя включать секцию только по наличию соответствующего HTML ID. Должны быть доступны данные, разрешённые claims и работающий CTA.

## 4. Что требуется от будущего renderer

Минимальный runtime contract должен уметь:
- принимать отдельный module manifest с решениями и порядком;
- маппить `moduleId → sectionId/component → supported variant`;
- поддерживать несколько moduleId внутри одного section/component;
- включать/исключать секции без пустых мест, битых якорей и несуществующих CTA;
- валидировать, что каждый включённый модуль имеет renderer, данные, медиа и QA criteria;
- сохранять индивидуальный порядок модулей для конкретного ЖК;
- формировать отчёт о модулях, которые не поддержаны текущим renderer.

Это целевое требование. Оно не реализовано в текущем K15 HTML только на основании обнаруженной разметки.

## 5. Ограничения проверки

- Проверены исходные section IDs, ключи `MODALS`, статические `data-modal` и наличие маркеров manifest/config.
- Не проверялась достижимость каждого modal key через все возможные JS event handlers.
- Не проверялась фактическая визуальная композиция всех модулей на физических устройствах.
- Браузерные smoke-тесты K15 проверяют только описанные в [K15 Product and UX Gap Audit](K15_PRODUCT_AND_UX_GAP_AUDIT_2026-11-05.md) сценарии.
