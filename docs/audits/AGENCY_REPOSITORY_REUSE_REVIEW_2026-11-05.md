## Не переносить напрямую

### 1. Старую JSON Schema

Agency использует другую структуру паспорта: `dataVersion`, `positioning`, `audiences`, `modules`, `design`, `claims`, `commercial`, `technical` и другие поля. Текущая схема KLanding использует `project`, `facts`, `advantages`, `infrastructure`, `offers`, `assets`, `contentStrategy`, `verification`. Замена схемы сломает текущие промпты и пример паспорта.

### 2. Старый config generator

`scripts/build-project-config.py` формирует legacy `project-config.*.js` и `content-config.*.js`, ожидает другую схему и другой контракт статусов. Прямое копирование не создаст рабочий адаптер для текущего runtime. Сначала нужен точный mapping и тесты преобразования.

### 3. Старые K15 HTML/ZIP

В Agency есть K15 HTML и архив v27.1. Это полезный материал для UX-аудита, но не универсальный движок. В собственном аудите Agency отмечены конфликты по количеству квартир, планировкам, цене, сроку, типам квартир, парковке, акциям, endpoint и аналитике. Факты и коммерческие значения нельзя переносить без актуальных первичных источников. Медиа требуют проверки принадлежности и прав.

### 4. KEY OS / CRM / backend / CFO / Avito

CRM, backend, tenant isolation, финмодели, KPI, Avito-агент и операционные документы относятся к другим продуктовым контурам. Их не нужно смешивать с генератором лендингов. Можно ссылаться на них отдельно при разработке всей бизнес-системы KEY.

## Важные архитектурные идеи из Agency

1. Движок, профиль ЖК, контент, манифест модулей, медиа, реестр claims, lead contract, analytics contract и QA report должны быть разделены.
2. Пустые данные означают отсутствие контента, а не fallback на K15.
3. Каждый модуль выбирается по вопросу аудитории, доказательной базе и роли в воронке.
4. Каждое преобразование паспорта должно создавать отчёт о пропущенных, конфликтных и неподдерживаемых полях.
5. Наличие функции в коде не равно её работающему пользовательскому сценарию.
6. Статический анализ, браузерная проверка, тест реального устройства и интеграционный тест — разные уровни готовности.

## Следующий технический шаг

Сопоставить выбранные `moduleId` с реально существующими компонентами K15/runtime, отметить поддерживаемые варианты и пробелы. Затем спроектировать адаптер под текущую JSON Schema. Не переносить legacy generator до завершения mapping и не переписывать K15 до проверки исходной реализации.
